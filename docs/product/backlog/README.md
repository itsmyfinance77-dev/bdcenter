# بک‌لاگ توسعهٔ سایت مرکز توسعه کسب‌وکار

این پوشه برنامهٔ توسعهٔ همین سایت (`bdcenter.yazdccima.com`) است: هر کاری که
ساخته شده، در دست ساخت است، برنامه‌ریزی شده یا منتظر پاسخ مرکز است، به شکل
**اپیک** (یک حوزهٔ بزرگ کار) و **استوری** (یک قابلیت قابل‌تحویل). خواستهٔ
مالک پروژه (۲۰۲۶-۱۰-۰۴): «سیستم backlog و epic و story» برای برنامه‌ریزی
همین پروژه، نه قابلیتی در پنل.

## ساختار

- هر اپیک یک فایل است: `EP-BD-<شماره>-<نام>.md`.
- استوری‌های هر اپیک در همان فایل‌اند، با شناسهٔ `ST-BD-<شمارهٔ اپیک>-<شمارهٔ استوری>`،
  مثلاً `ST-BD-06-03` (سومین استوری اپیک ۶).
- شناسه‌ها هرگز عوض یا دوباره استفاده نمی‌شوند. استوری حذف‌شده با وضعیت
  «کنارگذاشته» و دلیلش می‌ماند.
- پرسش‌هایی که پاسخشان با مرکز است در
  [`../open-questions.md`](../open-questions.md) با شناسهٔ `OQ-BD-*` ثبت
  می‌شوند و استوری به آن‌ها پیوند می‌دهد.

## قالب هر استوری

```markdown
### ST-BD-06-03 · عنوان کوتاه

- **استوری:** به‌عنوان … می‌خواهم … تا …
- **معیارهای پذیرش:**
  - …
- **اولویت:** بالا · **وضعیت:** انجام‌شده
- **پیوندها:** [PR #10](https://github.com/itsmyfinance77-dev/bdcenter/pull/10) · کامیت `8b842a8`
- **پرسش‌های باز:** OQ-BD-… (یا —)
```

## وضعیت‌ها

| وضعیت           | یعنی                                                                     |
| --------------- | ------------------------------------------------------------------------ |
| برنامه‌ریزی‌شده | تعریف شده و می‌شود ساخت؛ هنوز شروع نشده.                                 |
| در حال انجام    | شاخه‌اش باز است و کار روی آن ادامه دارد.                                 |
| بازبینی         | PR باز است و منتظر بازبینی مستقل یا CI است.                              |
| انجام‌شده       | در `main` ادغام شده (معیار «انجام‌شده» در پایین برقرار است).             |
| منتظر مرکز      | بدون پاسخ یا دادهٔ مرکز نمی‌شود ساخت یا تمامش کرد (پرسش `OQ-BD-*` دارد). |
| کنارگذاشته      | دیگر لازم نیست؛ دلیلش کنار استوری نوشته می‌شود.                          |

## اولویت

- **بالا:** بدون آن سایت راه نمی‌افتد یا کار روزانهٔ مرکز می‌خوابد.
- **متوسط:** کار کارمندان یا مراجعان را به‌وضوح بهتر می‌کند.
- **پایین:** خوب است داشته باشیم؛ صبر کردن برایش هزینه ندارد.

## معیار «آماده برای شروع»

- متن استوری و معیارهای پذیرش روشن است.
- هیچ قاعدهٔ کسب‌وکاری حدسی نیست: قیمت، قواعد عضویت، متن گواهی و اطلاعات
  تماس فقط از مرکز می‌آید؛ هر ناشناخته در `open-questions.md` ثبت شده است.
- اگر تغییر معماری بزرگی دارد، ADR آن در `docs/decisions` نوشته یا اصلاح شده است.

## معیار «انجام‌شده»

یک استوری فقط وقتی «انجام‌شده» است که همهٔ این‌ها برقرار باشد:

1. در شاخهٔ خودش ساخته شده (`feat/…`، `fix/…`، `docs/…`) و با یک PR به `main`
   رسیده؛ هیچ کامیتی مستقیم روی `main` نیست.
2. **بازبینی مستقل** (نه توسط نویسنده) روی همان head انجام شده؛ همهٔ
   یافته‌های بحرانی و بالا رفع شده و بازبین تغییرات تازه را دوباره دیده است.
3. هر دو کار CI («Lint, types, tests, build» و «Browser tests») روی همان head
   سبزند.
4. ادغام به شکل squash و سنجاق‌شده به head انجام شده
   (`gh pr merge N --squash --match-head-commit <sha>`).
5. آزمون‌های لازم نوشته شده‌اند (واحد، پایگاه داده، مرورگر، به اندازهٔ کار).
6. هر تغییری در پنل مدیریت یا تغییری در سایت که کارمندان می‌بینند، در همان PR
   راهنمای کارمندان (`src/content/admin-guide.ts`، صفحهٔ `/admin/help`) را به
   فارسی ساده و با نام‌های خود پنل به‌روز کرده است (قاعدهٔ مالک، ۲۰۲۶-۱۰-۰۳).
7. `docs/HANDOFF.md` و همین بک‌لاگ (وضعیت و پیوند PR و کامیت) به‌روز شده‌اند.

## روال کار

- هر PR تازه شناسهٔ استوری‌اش را در عنوان یا متن می‌آورد (مثلاً
  `ST-BD-08-05`). اگر استوری‌ای برایش نیست، اول استوری را این‌جا بنویسید.
- با ادغام PR، وضعیت استوری «انجام‌شده» و کامیت squash آن نوشته می‌شود.
- استوری‌های «منتظر مرکز» با رسیدن پاسخ مرکز «برنامه‌ریزی‌شده» می‌شوند و
  پرسش مربوط در `open-questions.md` پاسخ می‌گیرد.
- کارهای پیش از روال PR (جلسه‌های ۱ تا ۴) با کامیت‌های خودشان ثبت شده‌اند؛
  کار جلسهٔ پنجم یک‌جا با [PR #1](https://github.com/itsmyfinance77-dev/bdcenter/pull/1)
  (کامیت squash `ed5358b`) ادغام شد و کامیت‌های اصلی شاخه‌اش در پرانتز آمده‌اند.
- بعدها می‌شود اپیک‌ها و استوری‌ها را به‌صورت Issue با برچسب و milestone در
  GitHub هم آینه کرد؛ مرجع همین فایل‌ها می‌ماند.
